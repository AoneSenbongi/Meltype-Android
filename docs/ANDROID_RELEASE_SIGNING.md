# Androidのリリース署名

2026年10月20日の利用者指示により、次のzenz版リリースから専用のリリース鍵で署名する。試作用のデバッグ鍵を正式配布へ使わない。

## 鍵の管理

鍵はソース管理外の `%LOCALAPPDATA%/Meltype/AndroidReleaseSigning` に保存する。RSA秘密鍵と自己署名証明書を作り、パスワードはWindowsの現在ユーザーのDPAPIで暗号化する。秘密鍵・パスワードをソース、配布ZIP、ログへ含めない。同じ鍵を以後の更新でも使い、既存鍵の自動再生成はしない。

別PCへ移す前に、秘密鍵と復旧可能なパスワードを安全な保管先へバックアップする。DPAPIの暗号化ファイルだけでは別PC・別ユーザーで復旧できない。バックアップの作成と復旧確認は未実施。

## 配布前の必須手順

1. `android/tools/AndroidReleaseSigning.ps1 -Action Initialize` で一度だけ鍵を作成する。
2. zenzの実装・モデル・ライセンス・端末試験が完了した、通常版の非debuggable APKを作る。学習用appIdや診断用manifestを正式配布しない。
3. 同スクリプトの `-Action Sign -ApkPath <入力APK> -OutputPath <新しい配布APK>` で整列・署名する。
4. `-Action Verify -ApkPath <配布APK>` で署名、有効な通常版appId、debuggable無効、16KB整列を再確認する。署名証明書SHA-256は保存した専用証明書と一致させる。
5. 実際に署名した最終APKを検証し、版番号・変更点・検証結果・既知の制限・移行手順と添付物を提示して、利用者の公開承認を得る。

スクリプトは既存の入力APKを変更せず、新しい出力先だけへ書く。専用鍵がなければ署名を停止し、デバッグ鍵へ切り替えない。通常のローカル診断ビルドには影響しない。

## 既存版からの移行

1.0.0と現在の学習版はデバッグ鍵で署名されている。新しい専用鍵へ単純に切り替えると上書き更新できない。1.1.0では下記の署名ローテーションを使用する。Android 15エミュレーターで標準appIdの公開1.0.0からの更新を確認し、UIDと既存10ファイルの内容を保持した。Android 8.xの端末上での更新と最終APKの実機確認は未実施。ユーザー辞書・設定・学習データを保持する移行方法を確認するまで、アンインストールやデータ消去を案内・実行しない。

この資料は次回配布の要件であり、zenz版の完成・移行の成功・公開を示すものではない。

`android/tools/Test-AndroidReleaseSigning.ps1` の9検査が通過。署名と独立再検証、入力APK不変、旧デバッグ証明書・既存出力・鍵の再生成・鍵欠落・debuggable・学習用appIdの拒否を確認した。証跡は `E:/prog/Meltype/Android/distribution/release-signing-validation-20261020/checks/result.json`。

## 1.1.0で検証する署名ローテーション

公開済み1.0.0の署名から専用証明書へ移行し、辞書・設定を保持した上書き更新を検証する。Android 9以降のv3署名は専用証明書を使い、Android 8.xとの更新互換性のためv2署名に旧証明書を残す。これは鍵がない場合のフォールバックではなく、旧鍵と専用鍵の両方を必須とする明示的な移行方式である。Android 8.x側に旧署名が残る点は公開前確認で明示し、承認前には公開しない。

`Sign-AndroidUpgrade.ps1`は公開済み旧APKの証明書と旧鍵を照合し、専用署名の検証後に署名履歴を作る。Android 9以上と8.xの各検証範囲で期待する証明書を別々に照合し、16KB整列も再検証する。署名履歴には公開証明書と移行の証明が含まれ、秘密鍵は含まれない。秘密鍵とDPAPI暗号化パスワードは引き続きソース・配布物へ含めない。標準パッケージの1.0.0→1.1.0が対象で、別パッケージの学習版からのデータ移行を示すものではない。
